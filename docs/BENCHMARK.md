# Frozen geometry benchmark

The benchmark measures constrained editable CAD generation, not finished product engineering. Development has 24 public cases (6 each of glasses frame/electronics enclosure, board enclosure, bracket, clip). Hidden test has 100 cases: 20 per family and 20 unfamiliar two-family compositions. Hidden numeric dimensions include interpolated values absent from development. Requests explicitly state millimetre dimensions. This is templated language and four fixed geometry families, not open-domain natural language understanding.

Freeze happens before development optimization. `freeze()` writes public development instances, protocol and SHA-256 commitments; hidden instances are generated with an undisclosed random seed and stored outside the project under `~/.cadforge-private/CoreWeave/hidden.json` with owner-only permissions. Do not read that file during development. Freeze is idempotent and cannot update an existing commitment. The checker, immutable witness builder and schema source hashes are committed; the development generator can improve. Any modification makes evaluation refuse to run. Any checker bug requires a documented benchmark version change before hidden evaluation, never a silent relaxation.

The evaluator passes only each public design brief to the runner. Expected contracts stay inside the evaluator. It releases aggregate successes, execution failures and measured costs only. It exclusively creates a single-use ledger per condition before evaluation; crashes also consume that evaluation. Do not retrain on hidden artifacts, inspect failed hidden designs or rerun conditions. The same OS account can technically read private fixtures: this is procedural separation, not a hostile-process security boundary. Strong leakage prevention requires a separate evaluator account/container or external service.

Every required check must pass for a point. Constraint values must match. Exported STEP geometry is reimported and checked against frozen cavity/aperture emptiness and wall material witnesses constructed from the hidden contract; exported editable Python must carry a literal matching SPEC; STL must parse, be watertight and match the delivered STEP volume within 2%. Delivered geometry must pass validity, positive volume, clearance, part intersection, wall witness and aperture tests. Its total bounding box must cover the expected envelope with no more than 20 mm additional extent on each axis; extra mounting features are permitted. At least the expected solid count and 35% of nominal reference material volume must remain. Enclosures additionally require at least two cylindrical screw apertures of the requested radius. The initial engine did not implement those mounting holes; a development repair added them without changing frozen witnesses. Composite interface/functional-opening validation is unsupported and always fails closed. These failures remain in the denominator. The immutable witness builder originated as a snapshot of the initial generator. It no longer imports the development generator, and does not enforce exact topology, so added mounting holes/features can pass. Envelope/probe tests do not establish every feature dimension or eliminate every pathological alternative; this remains a bounded geometry benchmark, not a complete engineering oracle. Source validation is a structural editability check; it does not execute arbitrary candidate source or prove arbitrary edits remain valid.

Before freezing, enclosure request scope was set to board housing, camera aperture, lid and screw mounting holes; ventilation is not an unimplemented base-case claim. Camera checks cover a circular aperture and board envelope only. Camera-module depth, lens optics, connectors, electronics heat, wiring, battery, lid retention, glasses comfort, attachment strength, manufacturing tolerances and material/FEA performance are not established. `engineering_ready` remains false. A geometric score must never be presented as a safe or functional wearable score.

Conditions are `none` (no learned commands), `retrieved` (fixed script retrieval) and `learned` (development-learned parameterized commands). Each receives the exact same frozen limits per case: 4 attempts, 12 tool calls, 12,000 model tokens and 120 seconds. Attempts/tool calls/tokens are counters from the instrumented runner; evaluator independently measures elapsed wall time. It rejects over-budget or missing/invalid counters. Wall time is a post-run check, not process preemption. Persisted learning must be disabled during all hidden conditions and all condition state snapshotted before running. Baseline script index, learned-library digest and development discovery cost belong in the run report. Equal maximum budget does not imply equal actual expenditure; both must be reported.

Use `evaluate_cases(development_cases, runner, mode, Budget(), feedback=True)` for development. Use `evaluate_hidden(runner)` once after development is complete. The callback is `runner(public_brief, mode, budget)` and returns `spec` (DesignSpec or dictionary), `exports` (python, step, stl paths), and `usage` or `cost` (attempts, tool_calls, model_tokens). `artifact_dir` with conventional `design.*` files is supported as an alternative. Hidden output intentionally omits per-case feedback. Actual run results are generated by the orchestrator, not stored as estimated scores here.
